# Vector rollout and recovery

Prepared instructions only. No SQL/ES/Redis/Kafka/provider change, deployment or backfill has been executed. Main sources are compiled; tests and runtime acceptance gates are unexecuted under the user's no-tests instruction.

## Operator sequence

1. Pause vector writers, schedule/manual LT refreshes, profile/post consumers and interaction dispatch/consumption while preparing schema. Back up SQL journals/outbox/audit/processing ledger together with ES and persistent Redis state. Inspect the existing schemas/mappings/topology; never point validation at configured live services without the operator's separate execution authorization.
2. Review and apply `user_vector_update_operations.sql` and `vector_interaction_outbox_and_audit.sql` BEFORE deploying any new writer. Verify unique operation/source identities, `row_version`, microsecond timestamps, ledger cursor columns and repost actor/post uniqueness. Resolve reported duplicates manually; retain existing audit/history. These are manual MySQL scripts, not automatic migrations.
3. Inspect `GET /user_detail_vector/_mapping` and `GET /post_vector/_mapping`. Apply `user_detail_vector_mapping.json` as the body of `PUT /user_detail_vector/_mapping`, and `post_vector_mapping.json` as `PUT /post_vector/_mapping`, then verify both 768-dimension cosine fields and keyword IDs/model/status/filter fields. Existing incompatible types/dimensions cannot be changed in place: stop, prepare a versioned index and an explicitly reviewed alias/config migration, validate retained raw vectors, metadata, OCC/tombstones and journal operation identities before resuming. Never infer model compatibility from 768 dimensions. The application uses fixed index names; an alias migration must preserve those names. No index switch is automated here.
4. Require standalone Redis (current multi-key Lua fails startup on configured Lettuce Cluster). Inventory actual topology and configure durable acknowledged persistence: AOF enabled, `appendfsync always`, no eviction of vector/version/journal-operation/ST-cursor keys. Verify backup/restore continuity with SQL/ES; mere absence of a cache is not proof of a new user. A cluster migration needs reviewed common hash slots for every script key before topology changes. ST bytes/model expire after one day; journal marker/version/ST cursor have no TTL. Retain SQL journal and processing ledger beyond ST expiry, including COMPLETED and SKIPPED rows. Inventory legacy ES `vector_version` versus Redis version before the first journal-backed write; do not lower ES history or guess a missing counter/marker.
5. Set `vector.feed.recommendation.enabled=false` explicitly on ALL instances for initial rollout. **Its code default is true.** Keep `vector.interaction.consumer.enabled=false` and `vector.outbox.enabled=false` (both code defaults false). Deploy the profile journal writer and dual-vector post writer after schemas/mappings are verified. Stop old full-entity/unfenced writers; do not run two canonical implementations in one group or use a second group to consume the same history. Profile/post existing listener groups remain `user-service`/`post-service`; canonical group defaults to `feed-service`.
6. Inventory canonical topic `user_interaction_events`, committed group offsets, existing ledger/cursors and actual broker partition count. Consumer defaults: `partition-count=1`, `generation=v1`, `group-id=feed-service`; configure the actual fixed partition count before enable. Preserve generation/topic/user partition/offset scope. Existing COMPLETED/SKIPPED cursors are checkpoints even when no live ST exists. To repartition/reset, pause all canonical processing and prepare an explicit SQL/Redis checkpoint/generation migration; changing the generation string alone is rejected. Do not replay historical outbox/audit as fresh canonical identities.
7. Inventory explicit user/post IDs in pages of at most 100 using the services below. Apply only reviewed pages, serially with a 250ms..60s interval (maximum four starts/second; choose a slower rate for provider/ES budgets). Save every result/page and rerun dry-run; QUARANTINED/FAILED/pending/model-unknown findings block completion. User seed is allowed only from a valid, confirmed-compatible profile while LT is missing/empty and learned history is not true. Existing nonempty LT, including unknown/incompatible learned LT, is preserved. Profile re-embedding requires the explicit boolean; no vector is relabeled. Deleted users are listed/skipped; live SQL users with ES tombstones or missing learned LT require operator recovery. Post repairs recheck SQL source, reuse compatible raw fingerprint, obtain coordinated author state, embed outside the lease, and commit captured OCC; deleted/rejected sources are fenced/skipped. Legacy orphan IDs lacking author metadata must be included explicitly in inventory; whole-index discovery is not implemented by these services.
8. Enable `vector.outbox.enabled=true` after outbox schema/topic validation, then independently enable `vector.interaction.consumer.enabled=true` after persistence/checkpoint validation. Observe parked records and repair-required alerts; errors do not ACK. Outbox/audit/source identities and processing ledger remain durable. After approved dual-vector backfill, checkpoint and acceptance gates, set `vector.feed.recommendation.enabled=true` consistently across instances. Do not delete `feed:<userId>` to switch modes: v2 mode/version invalidation removes owned recommendations while retaining fanout/seen; untagged nonempty v1 queues drain/expire.

Check deployed property names against `OutboxDispatcher` and `FeedInteractionConsumerConfig` before execution. These notes do not imply live configuration was inspected.

## Callable inventory/repair contracts

No new HTTP/admin route is added. Use an operator-controlled application invocation after separate authorization; calling `apply` is mutating and may call Gemini.

- `UserVectorRepairService.dryRun(List<String>) -> Flux<Inventory(userId, findings, seedAllowed, reembedProfileRequired)>`: read-only SQL/ES inventory; connection errors propagate, not missing-vector results.
- `UserVectorRepairService.apply(List<String>, Duration interval, boolean reembedProfile) -> Flux<Result(userId, status, detail)>`: rechecks seed eligibility under the common lease and shared journal/ST recovery, or reuses the authoritative profile refresh outside the lease. Never resets learned/nonempty LT. QUARANTINED and FAILED are per-ID operator results, not successful repair claims.
- `PostVectorRepairService.dryRun(List<String>) -> Flux<Inventory(postId, findings)>`; `apply(List<String>, Duration interval) -> Flux<Result(postId, status, detail)>`: shared rebuild/tombstone path; live tombstones and pending moderation are explicit skips. REBUILT_OR_FENCED requires a follow-up inventory and does not promise provider execution for already-current sources.

All pages require 1..100 trimmed nonblank IDs of at most 255 characters; duplicates are removed. Apply uses one in-flight ID and reactive delay; no blocking sleep, automatic startup backfill, unbounded scan or blind COMPLETED replay.

## Quarantine and restore

`VectorRepairRequiredException` (ST subtype `FeedShortTermRedisState.ContinuityException`) fails writers/shared snapshots and the full-feed pre-serve boundary, even when the queue is full. API adapters may wrap it as the cause of an existing AppException. Journal recovery happens before the journal check; ST recovery verifies already-applied pending cursor identities and runs its final check after pending completion. A pending Redis-success/SQL-failure window reconciles its stored identity without blending twice.

The latest COMPLETED PROFILE/LONG_TERM journal attempt is ordered by captured ES `baseline_seq_no`, not ID/time: a CONFLICTED attempt reuses its row. Its operation ID must match BOTH Redis's persistent journal marker and the corresponding current ES profile/LT operation ID; Redis version cannot be below current acknowledged ES vector version. CHECKPOINT is excluded. Legacy absence with no durable journal claim keeps missing-vector fallback. ST applied-state continuity excludes permanent SKIPPED; independent completed/skipped progress continuity preserves topic/generation/partition/offset and cursor operation identity. Expired acknowledged ST never resurrects old bytes.

On missing/regressed/malformed marker/version/cursor, changed/missing acknowledged ES state, or missing/changed unexpired ST, stop affected user processing and feed serving; pause canonical consumption/dispatch as needed. Preserve SQL/ES/Redis evidence and parked offsets. Do not delete the ledger, lower counters, change generation, reset LT, or reset a COMPLETED row to PREPARED. Restore a verified consistent SQL/ES/Redis backup, or have an operator reconstruct CURRENT ES journal identity/version and CURRENT canonical checkpoint from retained durable facts under paused writers. Redis journal markers are not ST dedup records. ST cursor recovery must use the latest acknowledged completed/skipped checkpoint; an unexpired applied snapshot can only be restored from its matching ledger desired state with the original remaining absolute expiry, never a new one-day TTL. If current ES/journal/ledger identity or learned LT cannot be proven, leave quarantined and perform a separately reviewed recovery; the supplied repair services intentionally do not bypass this boundary. No automated committed-state reconstruction is supplied, and no unlimited exactly-once guarantee is made.

## Rollback and acceptance gates

Set `vector.feed.recommendation.enabled=false` on all instances to rank/read retained compatible raw `content_vector`; author-only posts with no raw content become the defined no-input skip. V2 cached recommendations are invalidated on mode change without removing fanout. Stop the new canonical consumer independently if required (`vector.interaction.consumer.enabled=false`); retain outbox/journal/audit/processing checkpoints and prepared desired snapshots. Pending desired operations finish their captured inputs; toggling the flag is not a request to recompute them. Do not redeploy old full-save/unfenced canonical writers beside the new ones, delete new durability tables, or undo seed by resetting learned LT.

Unexecuted runtime gates: OAuth CREATE yields two user vectors and login/profile retry preserves learned LT; caption/hashtag post creates raw+recommendation metadata; REPOST yields ST+audit then scheduled LT; readers wait for writers; pending ES/Redis-success recovery finishes once; acknowledged Redis/ES rollback and skipped-only cursor loss quarantine all writers/full cached feed; natural ST expiry does not replay; fanout survives mode/version invalidation; SQL optimistic mapping, real Painless/Lua, Kafka rebalance/checkpoint and Spring deferred wiring work with deployed infrastructure. Source compilation is not evidence these runtime gates passed.
